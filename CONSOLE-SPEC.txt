this file documents the intended specification for kconsole.c and kconsole.h

for kconsole.h, use the "#pragma once" directive

Matrix16 implements up to 4 virtual consoles using the hardware pages for fast switching:
	VC0 = B800:0000
	VC1 = B900:0000
	VC2 = BA00:0000
	VC3 = BB00:0000

GENERAL RULES:
	keep everything as simple as possible
	prefer code readability by humans to "cleverness"
	use appropriate comments - not overly verbose, but enough for a typical C coder to understand
	don't chain loads of operations on a single line of code unless that's the only way

	DO NOT CALL THE BIOS ANYWHERE EXCEPT WHERE EXPLICITLY DOCUMENTED BELOW

	DO NOT ADD ABSTRACTIONS YET FOR SERIAL
		but keep it in mind - don't add anything that would make it impossible or extremely difficult to add serial console later

	DO NOT ADD ANY CLEVER SYNC PRIMITIVES

	REMEMBER THE TARGET PLATFORM IS 1980s HARDWARE - 8088 PROCESSOR WITH 512KB TOTAL RAM ON AVERAGE
	
	WE HAVE LIMITED RAM AVAILABLE FOR THE KERNEL AND THIS IS ONLY ONE PART OF THE KERNEL
	
	If you have to choose between two implementation approaches, prefer the approach that results in less memory use (including the code itself)

RULES ON ANSI AND OTHER CLARIFICATION:
	We only support a reduced subset of ANSI for now:
		cursor movement
		clear screen
		clear line
		basic colours
		and enough for tasks to be able to read standard arrow keys and home/del/backspace etc

	standard ctrl-s should produce ASCII 0x13
	backspace should produce \b
	enter should produce only \n (not \r or \r\n)
	arrow keys should produce standard escape sequences
		only enque on key press
	for sequences being written to ringbuffer, always ensure the ringbuffer has sufficient space for ALL the needed bytes before enqueuing, otherwise drop the input
	ANSI state should be local per-console, not global
	
ring buffers:
	keep the ring buffer very very simple
	it should have 256 bytes per console
	remember, ANSI sequences and anything else multi-byte must be written all together or dropped - no partial sequences

caps lock and num lock:
	caps lock:
		on press only (ignore release), toggle a boolean in the active console's state and change any letters coming into that console to uppercase if it's active
		on press, immediately set the hardware LED
		on console switch, check the boolean of the new console, and update the LED
	num lock:
		on press only (ignore release), as with caps lock, toggle a boolean in the active console's state, use it to appropriately determine whether numpad gives direction or numeric
		as with caps lock, set hardware LED, and ensure console switch updates the LED correctly too
	ignore scroll lock entirely for now
	ignore typematic rate for caps lock of course
	modifier keys like ctrl,alt,shift should be global
	keep track of whether caps or num lock is physically held and don't allow it to autorepeat

hardware LEDs:
	do this from 1 or 2 central functions that can be trivially stubbed out or disabled with a simple comment out if needed (for example, if the intended target doesn't support it)
	in fact, for now - please simply provide a means to set the hardware LED state in the global struct, and have the hardware LED change when switching console
		DO NOT do it within kconsole_kb_callback - just update the global struct, and set the LEDs when switching console only
		it is okay for now if this means they will be out of sync at first

cursor coordinates:
	use the BIOS to set the visible cursor location on active console
	for background consoles, just update the console state

		here is sample asm code for using the BIOS to update the cursor location, use it only for active console and when switching active console

		mov ah, 02h     ; Set cursor position
		mov bh, 0       ; Console/page number (0–3)
		mov dh, 10      ; Row
		mov dl, 20      ; Column
		int 10h

character echo:
	DO NOT do this
	typed characters should NOT automatically be echo'd back within kconsole.c

NEVER EVER EVER invoke the BIOS from inside kconsole_cb_callback, or do anything else that is dangerous from within an ISR context, as this function is ultimately invoked from the IRQ1 ISR

kconsole.c requires these functions and data:

	static console_state_t consoles[4]
		precise fields can be defined as needed to implement the API
		ignore the existing console_state_t struct in kmain.c for now - pretend no structs or datatypes in kmain.c exist
		use stdint.h for the integer types
		this needs whatever state needed, including the input ringbuffer

	static uint8_t active_console;

	static void (*kb_save_cb)(void);
		this is a function pointer for the save menu callback - to be invoked by kconsole if not NULL and the user presses ctrl-alt-s
	static void (*kb_switch_cb)(uint8_t console_num);
		this is a function pointer for the switch console callback - to be invoked by kconsole if not NULL and the user presses ctrl-alt-F1 through to ctrl-alt-F4

	void kconsole_init(uint8_t page_num);
		page_num is an enum or constant usually:
			PAGENUM_VC0=0
			PAGENUM_VC1=1
			PAGENUM_VC2=2
			PAGENUM_VC3=3
		this function will use a lookup table to find the address of that page in VRAM
		then it'll clear that page
		a global console_state_t struct will then store the current cursor position (initialized to 0,0) for that page
		this should do nothing if sent an invalid console number
	void kconsole_set_save_cb(void (*callback)(void));
		this is used to assign the kb_save_cb function pointer
	void kconsole_set_switch_cb(void (*callback)(uint8_t console_num));
		this is used to assign the kb_switch_cb function pointer
	void kconsole_switchto(uint8_t page_num);
		takes the same constants as kconsole_init
		switches using BIOS INT 10h, AH=05h, AL=page_num
		moves hardware cursor to whatever is in the global console_state_t struct
		this should result in that console now being visible on screen
	void kconsole_move_cursor(uint8_t page_num, uint8_t row, uint8_t col);
		updates the cursor position in the global struct
		if that page is active, moves the hardware cursor
	void kconsole_putc(uint8_t page_num, char c);
		properly handles standard ANSI control sequences etc, writes to the VRAM and updates cursor using kconsole_move_cursor()
		any state needed for handling ANSI control sequences can be held inside console_state_t struct
		obviously only writes to the relevant bit of VRAM as defined above - if not the current active console, this should still update the other page's VRAM and state
	void kconsole_kb_callback(uint8_t scancode);
		this is the "keyboard callback" which will be called from the ISR
		it should check the active console and append the character to that console's input ringbuffer (where kconsole_getc can read it)
		if the buffer is full, it should simply discard the character - but take care with key release state and do something sane for this
		we must NOT lose key release events and corrupt state
		this callback receives raw scancodes read from 60h by the rest of the kernel, it is responsible for turning that into something fairly sane as expected by an ANSI terminal
		assume XT scancode set 1
		special cases:
			if the user presses ctrl-alt-s, check if kb_save_cb is NULL, and if not then call that and do NOT append to the console's ringbuffer
				however, normal ctrl-s should still go to the ringbuffer - the intention being that tasks can still handle ctrl-s themselves
			if the user presses ctrl-alt-F1 through to ctrl-alt-F4, call kb_switch_cb (if not NULL) and pass the number 0-3 as the first param
	bool kconsole_getc(uint8_t page_num, char* out);
		this sees if there's any characters waiting on the "stdin" buffer for that console, if so it writes to *out and returns true
		otherwise it returns false
		this is STRICTLY NON-BLOCKING - if there's nothing in the buffer, it immediately returns false
